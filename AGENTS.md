# AGENTS.md

Django REST Framework job board (backend) + React frontend. Two independent apps, no monorepo tooling. Root `.env` is the single source for backend config.

## Layout

- `backend/` — Django 5 + DRF + Celery + MySQL. Custom user model `users.CustomUser`. JWT auth (simplejwt, `Bearer`), dj-rest-auth + allauth (mandatory email verification).
- `frontend/` — React 19 + Vite + TypeScript + Tailwind v4. Generated from AI Studio (README mentions `GEMINI_API_KEY`) but the real AI stack is Django → local Ollama (`agents/agent_bridge.py`, `OLLAMA_API_URL` default `localhost:11434`). Ignore the Gemini references.

## Backend

- Python venv lives at `backend/env/` (Python 3.14). Root `.venv` is unrelated. Use `backend/env/bin/pytest`, `backend/env/bin/python`.
- Tests: pytest only (`pytest.ini` sets `DJANGO_SETTINGS_MODULE=jobboard.settings`, `asyncio_mode=auto`). No linter configured.
  - Run a slice: `backend/env/bin/pytest jobs/tests/ -q`
  - API contract suite (no DB needed): `backend/env/bin/pytest core/tests/test_api_contract.py -q` — pins every frontend endpoint/method/response field against the drf-spectacular schema. Keep `EXPECTED_ENDPOINTS` / `EXPECTED_RESPONSE_FIELDS` in sync with the frontend.
  - Fixtures are aggregated in `backend/conftest.py` from per-app `tests/fixtures.py` (`user`, `job`, `company`, `user_tokens`, ...). Add new fixtures in the app's own `tests/fixtures.py`.
  - E2E seed (idempotent): `backend/env/bin/python manage.py make_test_user` — creates `e2e-seeker@jobboard.test` / `e2e-employer@jobboard.test` (password `E2ePass123!`), company `E2E Employer Co` and the sample job used by the Playwright suite. Usernames equal emails because JWT login authenticates by username.
- DB is MySQL via `pymysql.install_as_MySQLdb()`; `settings.py` reads DB creds from root `.env` with no fallback. Tests need a running MySQL (and Redis for anything touching Celery). `docker-compose.yml` provides `mysql:3306`, `redis:6379`, `backend:8000`, `celery_worker`, `frontend:3000` — it `env_file: .env`.
- Celery uses JSON serializers (`CELERY_TASK_SERIALIZER = 'json'`) → `.delay()` args must be JSON-serializable. Do NOT pass Django `UploadedFile` objects to tasks (breaks with `kombu.exceptions.EncodeError`); extract text/bytes in the view first.
- DRF 3.16.1 has NO async support: an `async def` handler is never awaited by DRF's sync `dispatch`, and Django 5.2 marks the view async → `TypeError: 'Response' object can't be awaited` at runtime. Keep views in `jobs/views.py` as sync `def`. If you must call an async agent service, bridge it with `async_to_sync` (asgiref), as `jobs/tasks.py` does.
- Delete job post is a soft delete: `perform_destroy` sets `status=ARCHIVED`, responds `204`.
- API schema generated by drf-spectacular: `/api/schema/`, `/api/docs/` (Swagger). Update `@extend_schema` on views to keep it accurate.

## Frontend

- `npm run lint` is `tsc --noEmit` (typecheck only, no ESLint). Run `npm run lint` then `npm run build` after changes.
- Tests: Vitest (unit/service/component) + Playwright (E2E). Commands: `npm test` (Vitest), `npm run test:coverage` (Vitest with v8 thresholds), `npm run test:e2e` (Playwright, needs the backend up on `localhost:8000` via docker-compose and seeded with `make_test_user`).
- `@/*` path alias resolves to frontend root (e.g. `@/services/api`).
- Demo Mode is ON by default: `apiFetch` in `src/services/api.ts` routes to `demoService.ts` (localStorage mocks) unless demo is disabled (`VITE_ENABLE_DEMO_MODE=false` or the localStorage toggle). Real API base from `VITE_API_BASE_URL`.
- Three things must stay in sync when endpoints change: the `src/services/api/` modules (re-exported by `api.ts`), the matching mock in `src/services/demoService.ts`, and the response types in `src/types.ts`. The backend contract suite asserts the endpoints/fields; the Vitest suite asserts the frontend↔mock sync.
- AI endpoints return a Celery `task_id` immediately (202); status is polled via `GET /jobs/task-status/<task_id>/` → `{ task_id, status, result }` (`result` is `null` until done). `useTaskStatus` (in `src/hooks/useTaskStatus.ts`) implements the polling and is used by `ResumeAnalysisModal`.

## Gotchas

- `backend/resumes/`, `media/`, `.env` are gitignored. Never commit secrets.
- `.env.example` (root) lists every required backend var (DB, JWT, EMAIL, CELERY, OLLAMA_MODEL_NAME). `SECRET_KEY`, `DB_*`, `JWT_SIGNING_KEY`, `CELERY_*` are required at import time — the app won't boot without them.
